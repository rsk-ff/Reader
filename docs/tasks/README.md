# Task documents

任务文件用于多回合开发和跨会话交接，不是让用户填写的工单。Codex 负责创建、更新和归档。

## When a task file is required

以下任一情况建立任务文件：

- 预计需要多个用户反馈或实现回合。
- 会调用 Pi。
- 涉及重要设计、多个模块或较高风险。
- 自动化验证后还要等待用户视觉/交互验收。
- 当前会话可能在完成前切换。

单回合即可完成的只读诊断、小修、打包或机械操作不必建立任务文件。

## Status values

- `in_progress`：代理可以继续执行具体下一步。
- `waiting_user_acceptance`：自动化验证完成，下一步是用户视觉或交互反馈。
- `blocked`：继续需要尚未获得的权限、外部状态或用户决定；必须写明解除条件。
- `done`：目标和必需验证已经完成，文件应移入 `archive/`。
- `cancelled`：目标明确终止或被替代，记录原因后移入 `archive/`。

## Lifecycle

1. Codex 从 [`TEMPLATE.md`](TEMPLATE.md) 创建 `active/YYYY-MM-DD-short-name.md`。
2. 开始实现前写清目标、现状、范围、验收、基线和继续任务所需的 `Related context`。
3. 每次实现、发现、用户反馈和验证后更新相应章节。
4. 等待用户验收时把状态设为 `waiting_user_acceptance`，并保留准确检查清单。
5. 完成时记录结果和剩余风险，移动到 `archive/`，更新 `docs/STATUS.md` 和需要的其他文档。
6. 同一连贯目标在新会话中继续使用原活动文件；独立目标创建新文件。

`docs/STATUS.md` 必须索引每个活动任务及其状态。若同时存在多个活动文件，新会话只选择与当前用户目标匹配的一项，不自动读取或合并其他任务。

## Rules

- 文件必须自包含：不了解旧会话的人只读任务文件、其中 `Related context` 指向的资料、Git 状态和相关代码就能继续。
- `Related context` 只列继续任务必需的产品、架构、决策、开发文档和代码入口；不把整个文档树列为必读。
- 记录事实、决定和证据，不粘贴完整构建日志、完整 diff 或代理推理。
- `Progress` 反映真实状态，不能把“代理声称完成”写成已验证。
- `Next action` 始终只有当前最具体的下一步。
- 归档文件不是默认上下文；只有当前任务明确引用时才读取。
- 用户不负责编辑、移动或清理任务文件。
